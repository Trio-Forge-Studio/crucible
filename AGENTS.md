# Agent instructions

Crucible is Trio Forge's TypeScript game framework for Roblox. It replaced Flamework. This repository holds the runtime package, the TypeScript 7 compiler that builds it and the games that use it, the `crucible` command line, and the user guides. `design/architecture.md` sets where code belongs, and `design/roadmap.md` orders the refactor that moves it there.

## Layout

- `packages/crucible` is the single runtime package, `@trioforge/crucible`. Its `@rbxts/charm` peer is pinned to exactly the version the specs run against, because ownership and ServerSync read and edit Charm's nodes, and `src/internal/reactive/charm.ts` checks those behaviours when the runtime loads. Adopting another Charm release, including one with `littensy/charm#71`, means running the specs against it and moving the peer, the devDependency, the sample's and template's version, `CHARM_VERSION` and `design/stack.md` together.
- `packages/crucible/src/index.ts` is the shared-safe root. It must never import or re-export server or client code, including through transitive imports.
- `packages/crucible/src/server/index.ts` and `src/client/index.ts` are the side entries. The package exports map resolves side entries under TypeScript 7 bundler resolution.
- `@rbxts/charm` is a required peer dependency of the runtime, pinned to exactly `0.11.1`, and a devDependency for its own build. The pin is exact because the runtime checks Charm's behaviour when it loads, so moving it means rerunning the reactive specs against the new release. It is never a hard dependency and never re-exported. Charm owns values, and the runtime owns lifetimes in `src/internal/reactive/ownership.ts`. `@rbxts/vide` is an optional peer at `^0.6.1` that only the `ui` entry requires. It is also a devDependency, because the `ui` build, the `ui-*` specs and the compiler's JSX fixture in `crates/compiler/tests/jsx/vide` resolve it from the runtime's `node_modules`. No entry imports `@rbxts/vide-charm`. A game that renders UI installs Vide and `vide-charm` next to Charm.
- `packages/crucible/src/ui/index.ts` is `@trioforge/crucible/ui`, the headless UI primitives of the retired `@trioforge/anvil`, on Vide. It is the only module that imports `@rbxts/vide`, and no other entry imports it, so the root, server and client entries load without Vide installed, as `test/subpaths.luau` checks. Its `.tsx` files compile with the runtime tsconfig's `jsx: "react"` and `jsxFactory: "Vide.jsx"`. It reaches services through `game.GetService`, so the runtime has no `@rbxts/services` peer. `modalOpen` is a Charm atom, so gameplay computeds can track it. The game supplies input, sounds and the menu claim through the adapter it installs with `installAnvil`. `test/ui-*.luau` are Anvil's specs, run on Vide's reactive core with fake services through `test/lib/ui-harness.luau`.
- `packages/crucible/src/util/random/index.ts` is `@trioforge/crucible/util/random` and `src/maths/spline/index.ts` with `curve.ts` is `@trioforge/crucible/maths/spline`. They are the retired `@trioforge/random` and `@trioforge/spline` packages, moved in unchanged, because `Rng` draws the same numbers from a seed on every client and server and games save its state. Do not change what either draws or returns. Neither imports anything, and no other entry may import them. There is no `util` or `maths` entry. The transform allows importing both under CRU004. `test/lib/random-golden.luau` and `test/lib/spline-golden.luau` hold answers recorded from the published packages, so a change that moves an answer fails the specs.
- `packages/crucible/src/testing/index.ts` is `@trioforge/crucible/testing`, which builds one Subsystem or behaviour in a Lune spec without `boot`. Game code cannot import it, because CRU004 rejects it. Only specs that load the built game import it, and no other entry may.
- `examples/sample-game` imports the root, each side entry and the `ui` entry through workspace dependencies. Its Rojo project maps the runtime's `out` folder under `ReplicatedStorage.rbxts_include.node_modules.@trioforge.crucible`. Mapping the whole package folder would add the package's own `node_modules`, and `TS.getModule` would find its copy of Charm before the game's.
- `docs` holds the user guides, one plain Markdown topic per file. `crates/docs` is `crucible-docs`, which embeds them and searches them, and the `crucible` binary links it. A new topic goes in its `TOPICS` list, or its tests fail. `crucible docs <topic>` prints one as Markdown when stdin or stdout is not a terminal, and opens it in an interactive reader when both are. A `mermaid` fence must render with `mermaid-text`, or the `crucible-docs` tests fail. The CLI build still succeeds, warns, and embeds that fence's source as its drawing. Each topic starts with `# Title`, a blank line, and a one-line summary that ends with a period. Document only what the code exports today. `test/docs.test.mjs` type-checks every `ts`, `typescript`, and `tsx` block against the runtime package.
- `specs` holds the TLA+ models that `cargo xtask tla` checks, one folder each. `specs/provision` models `crucible provision`, which PR 8 of `design/roadmap.md` implements.
- `test` holds Lune specs. `.lune/test.luau` uses the `@trioforge/tooling` runner. The specs load the built place through roblox-ts's runtime and assert subpath resolution and root isolation.
- `packages/compiler-types` is `@trioforge/compiler-types`, the compiler types with the three iterator parameters TypeScript 7 requires. All tsconfigs use it. It releases with the CLI. `test/compiler-types.test.mjs` checks the runtime and sample with tsrs.
- `crates/compiler` is `crucible-compiler`, the TypeScript 7 compiler in `design/compiler.md`. It checks a tsconfig with tsrs, fills a fact table, and lowers each file to Luau from the syntax tree and the facts alone. The fact pass also reports CRU032 to CRU034, the Luau pitfalls any roblox-ts code can hit, which keep Crucible's numbers. JSX lowers to `jsxFactory` calls under `jsx: "react"`, such as `jsxFactory: "Vide.jsx"`. Automatic JSX modes and `jsxImportSource` are compile errors. CRU028 to CRU031 and CRU037 are retired; do not reuse their numbers. `compile` and `analyze` take a `Target`: `Package`, or `Game` with an `InstanceMap` and the include folder, which reaches packages and the runtime library through the place. The compiler never reads a Rojo project. `crucible-project` reads it into the folders and files that `InstanceMap::new` takes, and the CLI and the transform's `compile` example join the two. `Game` also takes `VirtualModule`s, each an import specifier with no file behind it, such as `crucible:experience`. The compiler emits its Luau at the path it names in the output folder and resolves the import through the instance map, and the program declares its types with `declare module`. Nothing passes one yet; `design/architecture.md` gives it to the experience bindings. The compiler crate vendors roblox-ts 3.0.0's `RuntimeLib.lua` and `Promise.lua` in `roblox-ts/` with roblox-ts's MIT license and, for `Promise.lua`, roblox-lua-promise's, and `write_include` writes them. tsrs types stay in its `program`, `extract`, `tree` and `extension` modules. `compile_with` and `analyze_with` take extensions, which implement the `extension` module's `Extension` trait: `name`, then `begin_program`, `extract_file` and `finish_program` around extraction, and `lower_expression`, `lower_call` and `lower_class_tail` in lowering. An extension reads syntax through the public part of the tree view and the checker through the `Symbol`, `Type` and `Signature` handles, so it never names a tsrs type, and it keeps its own facts keyed by `SiteId`. A lowering calls into a runtime module through a `HelperModule` it declares, which each file that uses the module imports. `tests/extension.rs` holds a test extension that uses every hook. `crucible build` compiles each place of `crucible.toml` in a hidden `crucible __compile` child, because tsrs never frees a program. Its tests read `packages/crucible/out` and `build/sample-game.rbxl`, so run `pnpm build` first. The tests that run the emitted Luau need `lune` on PATH, and the virtual module one also needs `rojo`. They are ignored by default, so run them with `cargo test -p crucible-compiler -p crucible-transform -- --ignored`. CI runs them in the Linux `cli` job. The fact table and `analyze` are public only with the `test-support` feature. The crate's tests and examples turn it on through a dev-dependency on the crate itself. `pnpm run test:compiler` builds the runtime and the sample game with the compiler and runs the Lune specs against them in a temporary directory, after `pnpm build`. `pnpm check` builds both artifacts with the compiler. CI also reruns the isolated compiler specs.
- `crates/transform` is `crucible-transform`, Crucible's compiler extension, and the CLI compiles through its `compile`. It depends on the compiler and `crucible-abi`, and the compiler depends on neither. Its `begin_program` checks the ABI handshake: it reads `crucibleAbi` from the installed `@trioforge/crucible`'s `package.json`, treats a missing field as ABI 1, and fails the compile with a TS90000 error that names both versions when they differ. It owns registration and dependency injection: the CRU001 to CRU003, CRU005 and CRU007 to CRU016 rules over classes, `inject` and `attribute`, `defineClass` after each registered class, and the `inject` and `attribute` macros. It owns the network, replicated, data and config declaration macros and `receive`, with their wire schemas and the CRU017 to CRU027 rules, and CRU010 and CRU012 where a declaration breaks them. It owns `boot`, whose CRU006 rule resolves each load glob through the place's instance paths, and CRU004, which allows the subpaths in `crucible_abi::SUBPATHS`. It owns the lints over Crucible's classes, CRU035 and CRU036, and CRU038, which rejects `effect`, `effectScope` and `onCleanup` from `@rbxts/charm` in game code. `cargo run -p crucible-transform --example compile -- <tsconfig> <out> [<project> <include>]` writes the Luau of a package or a game, and the runtime's build and the Lune specs' consumers compile through it. Its `test-support` feature exports `analyze` and the facts it keeps. `tests/transform.rs` owns the registration and rule tests, `tests/network.rs` the network, replicated, data and config tests and `tests/typed_lint.rs` the CRU035, CRU036 and CRU038 tests, with their fixtures in `tests/transform-fixtures`, and `tests/sample_game.rs` checks the sample game through the transform.
- `crates/luau` is `crucible-luau`, the Luau AST and printer that the compiler lowers to. Like the compiler, it names nothing of the framework.
- `crates/abi` is `crucible-abi`, the one table of the ABI between the transform and the runtime: each emit function with the parameters compiled code passes, the registration record fields, the `n` schema builders, the `t` checks, the subpaths CRU004 allows, and the ABI version. `cargo xtask abi` writes `packages/crucible/src/emit/abi.d.ts` from it, and `emit/index.ts` satisfies that declaration through a type-only import, so tsrs fails the runtime build, and `pnpm check`, when the runtime drifts from the table. `cargo xtask abi check` never reads the runtime's code: it fails only on a stale `abi.d.ts`, a `crucibleAbi` that differs from `VERSION`, or a missing export for a subpath games may import. It is a `.d.ts` because a `.ts` file would compile to a Luau module. The runtime's `package.json` records the version in `crucibleAbi`. Raise `VERSION` on any change a compiled game would notice, then run `cargo xtask abi` and update `crucibleAbi`.
- `crates/oc` is `crucible-oc`: the Open Cloud transport, the outcome judge, credentials, and the safety, retry, auth and payload types that `crates/oc-registry` re-exports. The transport reports notes, traces and accepted writes to an injected `Sink` and reads time and sleeps through an injected `Clock`. The key comes in as values. `crates/cli` reads `CRUCIBLE_OC_API_KEY` and parses `.env`, because only it reads the environment. Its `ops` module holds the typed operations provisioning calls for developer products, game passes and badges: each is an `Op<T, S>` whose `S` is its retry rule (`Read`, `Idempotent` or `Unsafe`), and `Transport::run` returns the parsed reply. Creates are `Unsafe`, so a lost answer is never repeated. Once a write may have landed, because an attempt got a 2xx or a 5xx or lost its answer after it was sent, `run` returns the parsed reply or exit 5, never exit 7, and a reply it cannot parse becomes an error that names the operation and the field and keeps the reply and any ID in it. A list op is a `List`, which only `Transport::list_all` reads: it follows the page tokens to the end and fails, rather than return part of the list, on a token sent twice, on more pages than the cap, and on a page without the next-page field the registry requires. `tests/ops.rs` runs them against a fake server. `tests/live.rs` calls a staging universe and is ignored, so neither `cargo test --workspace` nor CI runs it: `CRUCIBLE_OC_API_KEY=… CRUCIBLE_STAGING_UNIVERSE=… cargo test -p crucible-oc --test live -- --ignored`, plus `CRUCIBLE_OC_LIVE_WRITES=1` for the test that writes one product.
- `crates/project` is `crucible-project`, the `crucible.toml` model and parser, and its `rojo` module, which reads a place's Rojo project and the projects it nests into folder and file mappings. Its `experience` module holds the file's `[experience]`, `[products]`, `[passes]` and `[badges]` tables and each environment's overlays, with the line of each key. `Manifest::parse` reads the `crucible` minimum version before the strict parse, with a line scan of the top-level keys that skips multi-line strings and stops at the first table header, then a lenient pass. `schema()` is the JSON Schema of the file: `cargo xtask schema` writes it to `crates/project/crucible.schema.json`, `cargo xtask schema check` fails when it is stale, and the CLI's npm package ships it.
- `crates/iac` is `crucible-iac`. `model` turns the experience tables into resources and checks the rules that span tables, `lock` and `journal` read `crucible.lock` and `.crucible/journal/<env>.json`, and `plan` computes what `crucible provision` would do without a network call. `crucible plan` prints it. It depends on `crucible-project` and never on the compiler, the transform or tsrs.
- `crates/cli` is the `crucible` command line in the root Cargo workspace. `crucible oc` calls Roblox Open Cloud and keeps the JSON-document and exit-code contract in `docs/oc.md`. `crates/oc-registry/spec/registry.json` is generated by `cargo xtask spec build`. Do not edit it by hand. `xtask` also holds the refactor checks in "Refactor checks" below.

## Checks

Run `pnpm install --pm-on-fail=download` and `rokit install`. Keep the lockfile after dependency changes. Rokit pins the Roblox tools, and the root `rust-toolchain.toml` pins Rust to the version the pinned tsrs SHA requires. CI installs Rust from that file. Vite+ configures TypeScript lint and formatting in `vite.config.ts`.

Run `pnpm check` before calling a change complete. It must exit 0. It checks formatting and lint, compiles the runtime with the transform's `compile` example in package mode, emits its declarations with tsrs, builds the sample into `build/sample-game.rbxl` with `crucible build` through `cargo run`, and runs the Lune specs. `pnpm fmt` fixes TypeScript, configuration, and Luau formatting. Fix failures at their cause.

For changes under `crates` or `xtask`, run `pnpm build` from the repository root before the npm package test. Also run `cargo fmt --all --check`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo xtask spec check`, `cargo xtask abi check`, `cargo xtask schema check`, `cargo xtask arch`, `cargo test --workspace`, `cargo xtask golden check`, and `node --test crates/cli/npm/package.test.mjs` from `.`. CI runs them on Ubuntu and Windows.

`cargo xtask tla` model-checks each TLA+ spec under `specs/` with TLC, then applies each mutant in the spec's `mutants.toml` and fails unless TLC finds a counterexample to the property the mutant names. It needs Java 11 or later on `PATH` or in `JAVA_HOME`, and downloads TLC 1.7.4 into `target/tla`, checking its SHA-256, unless `TLA2TOOLS_JAR` names a jar. CI runs it in the Linux `cli` job, so run it for changes under `specs` or `xtask/src/tla.rs`. `specs/provision/README.md` states the provisioning model's properties and assumptions. Change a spec and its `README.md` together.

The Lune loader supplies only the engine behavior needed to execute the sample imports. A passing Lune spec does not prove gameplay behavior in Studio.

## Refactor checks

Three `cargo xtask` commands, run from `.`, let a pull request prove itself without a line-by-line read.

- `cargo xtask golden check` builds the runtime and the sample game from clean with their own `build` scripts, hashes every file they write, and compares the hashes with `xtask/golden.txt`. It prints each changed, added and removed path and fails on any difference. It also fails, on record and on check, when an output folder holds no file, when the place is not a file, or when the baseline is empty or malformed. CI runs it on Ubuntu and Windows, because the output must be identical on both. `cargo xtask golden record` rewrites the baseline. Record it only in a pull request that means to change output, and list the changed files in its body.
- `cargo xtask golden check --fd <path>` also builds a Fragile Delivery checkout. It builds a temporary copy with this repository's `crucible`, so the checkout is never written to. FD's baseline is local, in `build/golden/fd.txt`, so run `cargo xtask golden record --fd <path>` on the base commit first.
- `cargo xtask arch` checks the five rules of `design/architecture.md` and compares the violations with `xtask/arch.txt`. It fails on a violation the list lacks and on a listed one that no longer exists. `arch record` rewrites the list, so the check alone does not stop the list from growing. `cargo xtask arch --base <rev>` adds the ratchet: it also fails when a violation is new against the list at `<rev>`, or occurs more often than there. CI runs it on every OS with the pull request's base, or `HEAD^` on `main`. After you fix one, run `cargo xtask arch record`. Never record a new violation to pass the check.
  - Rust is parsed with `syn`, starting from each crate's library, binary and build targets and following `mod`, `#[path]` and `include!`, without `#[cfg(test)]` items. Tests, examples and benches are other targets and are not read. An `include!` of a build script's `OUT_DIR` is not followed, because the build script is read.
  - Rules 1 and 4 count string literals, with escapes resolved. A name assembled from several literals is not counted, whether at compile time, as `concat!` does, or at run time, as `format!` does, and neither is coupling by meaning, such as the compiler's `MacroKind::Crucible` and `uses_crucible`. PR 4 and PR 5 remove that coupling. Rule 4 skips the one-letter ABI names `n` and `t`, because a one-letter string is too common to scan for.
  - Rule 3 counts any path through `std::env::var`, `var_os`, `vars` or `vars_os`, however it is imported, and any rename or glob import of `std::env`. It does not see environment reads through another crate, such as `libc::getenv`.
  - Rule 5 tokenizes each TypeScript file the runtime root reaches, so comments and strings cannot hide an import. It counts every import that is not type-only, including `require(..)` with a string literal and every `import(..)`, even one in a type, because `typeof import("x")` and `import("x").Name` can be values too. Name such a type with `import type`. A non-literal `require`, such as the boot glob's, is not an edge. A declaration it cannot read fails the check.
  - A change under `xtask` changes the checks themselves, so its commit is always `Review: read`.
- `cargo xtask proof [<base>]` prints the proof table for a pull request body. It runs golden against the baseline at `<base>`, runs the arch ratchet against the list at `<base>`, runs `abi check`, and lists each commit since `<base>` with its review kind. `<base>` defaults to `main`. Golden runs once, at HEAD, not per commit.

Every commit ends with a `Review:` trailer.

- `Review: mechanical` marks a commit that only moves, renames, updates paths or regenerates files. `proof` flags each rename under 95% similarity, each added, deleted or copied file, each binary or mode change, each hunk that adds or removes lines, and each line that is not byte-identical to the old one, whitespace, line ending and final newline included, outside path words swapped inside a string literal of the same quote or, in YAML and TOML, anywhere on the line. A word that holds a backslash is never a path word, so a changed escape sequence is flagged. It accepts changes to `golden.txt`, `arch.txt`, `crates/oc-registry/spec/registry.json` and `packages/crucible/src/emit/abi.d.ts`, whose CI checks compare them with what their commands write, and it lists every path edit it accepted under the table.
- `Review: read` marks every other commit.

Each commit passes `pnpm check` on its own. A pull request body has these parts, in order:

1. **Story.** Two sentences on what changes and why.
2. **Proof.** The output of `cargo xtask proof main`, pasted unedited.
3. **Read.** The commits and files to read, in reading order.
4. **Skim.** The mechanical commits, each with its evidence that it changes no logic.
5. **Not in this PR.** What a reader might expect here, and which pull request has it.

## Cleanup

Every Cargo build writes `target` in its own worktree, and each one grows to several gigabytes. Do not set `CARGO_TARGET_DIR` or clone the repository into another folder, such as `C:\build` or a temporary directory, because nothing cleans those up. Before you hand back a task that ran Cargo, run `cargo clean` from `.`, whether the task passed, failed, or stopped. Leave the worktree itself in place, because the thread that owns it may resume. Never clean another agent's worktree.

## Conventions

- Use Conventional Commits with a scope, such as `chore(repo): scaffold the workspace`.
- Name branches `<type>/<short-description>` and open PRs into `main`.
- A PR that resolves a Linear issue puts `Closes <ID>` in its body, such as `Closes CRU-12`. Branch names carry no issue ID, so the body links the PR to the issue.
- Push with an explicit refspec, such as `git push origin HEAD:refs/heads/chore/scaffold`.
- The pre-commit hook runs staged checks, and the pre-push hook refuses pushes to `main`; `pnpm install` installs both.
- Use squash merge and delete the branch after merge. Do not merge without task authorization.
- Comment only a non-obvious reason that the code cannot express.
- The runtime and CLI use MIT. Publish npm packages only through the tag release workflow. Publishing a release, creating secrets, pushing release tags, and changing repository settings require separate authorization.
